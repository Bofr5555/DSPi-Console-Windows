## 3. Phases

The order runs from the non-Link catch-up (Phases 0-4) to Link (L0-L6), and everything ships together as v1.1.6 final (N11). Some Link phases depend on Phase 1 and Phase 2: board names, RTA_CONFIG and analyser sharing are Link prerequisites as well as features in their own right.

Per CLAUDE.md, Claude builds and runs unit tests, and **the user does every in-app and hardware check**. Every phase ends with a hand-off listing what to try.

**Whenever a step needs a DSPi**, local over USB or remote through a hub or bridge, Claude stops and asks the user first (user instruction, 2026-11-08). Claude says which board is needed, on which machine and how it should be connected, then waits. Builds and unit tests need no board.

### Phase 1: Firmware 1.1.6 protocol catch-up (M, about 1 week)

Mac references: `Constants.swift`, `Commands.swift`. Firmware specs: `output_latency` (in `current_architecture.md`), `input_source_names_spec.md`, `device_name_spec.md`, `buffer_statistics_spec.md`, `control_surfaces_spec.md` (its §2.4 numbers are stale; the code says caps 22 / 81).

1. **Output latency, `REQ_OUTPUT_LATENCY` 0x03, wIndex 2.**
   - **Wire format:**
     - OUT sends a 1-byte option ID.
     - IN with wValue 0 returns 12 bytes: `requested_id, effective_id, effective_us u16, target_frames u16, batch_frames u16, pending u8, option_count u8, rsv u16`.
     - IN with wValue 1 returns `option_count` × 8-byte entries: `id, flags (0x01 stream-only, 0x80 runs-as-itself on the current source), latency_us, batch_us, effective_us`.
     - A STALL on the status read means unsupported.
   - **Settings › Globals "Latency" picker:**
     - Built from the device table.
     - Staged through `IPendingChangeTracker`.
     - Device-global; never in a preset.
     - After a SET, poll status (40 × 100 ms) until `pending` clears, then re-read the table.
     - Re-read the table when the input source changes.
     - Caption: "Values less than 2ms have no effect upon USB Audio", plus "runs as X ms" when effective ≠ nominal.
2. **Input source names, 0x54 SET / 0x55 GET.**
   - **Wire format:**
     - wValue = source 0..6.
     - 32-byte NUL-padded printable ASCII, at most 31 characters.
   - **Probe:** GET source 0. A reply shorter than 32 bytes means old firmware, which must never receive the SET.
   - **Notify 0x0F** (40 bytes): source at byte 4, ParamSource at 5, name at 8..39. All zeros means cleared.
   - **UI:**
     - A "Source Names" section at the end of the Inputs settings page, staged with a per-row unsaved dot.
     - Right-click on the sidebar source picker for Rename / Use Built-in Name.
     - Names replace the hard-coded labels in:
       - `MainWindow.xaml.cs` `RefreshSourceComboBox`
       - `ControlSurfaceModels.cs:424`
       - `PresetSnapshot.cs:700` (the unsaved-changes list)
3. **Board device name, 0x56 SET / 0x57 GET.**
   - **Wire format:** wValue 0, same 32-byte rules as the source names.
   - **Probe:** the GET alone. A STALL or a short reply means unsupported.
   - **Notify 0x10:** same layout as 0x0F.
   - **UI:**
     - A "Device Name" field on Global Parameters, saved after any source names.
     - Filter the field as the user types; trim the name and close gaps.
     - The device picker shows each board's name, cached per serial for the session.
4. **Control-surface caps v21/v22.**
   - Noun 79 PRESET_SAVE: trigger only, named "Save Preset".
   - Noun 80 OUTPUT_LATENCY: an enum, value = option ID − 1, labelled from the latency table, with the fallback labels "0.67 ms" … "8 ms". It reads back the requested option.
   - Rename the category "Input & Presets" to **"Device"**. It holds Preset, Reload, Save Preset, Input Source, LG Sync and Target Latency.
   - (Moved to Phase 3: rename "Frequency" to "Freq" on display-page rows, part of the Mac's display-page layout.)
5. **Stats.**
   - **Fine buffer fill:** `REQ_GET_BUFFER_STATS` per-slot bytes 6-7 hold `fill_centi_pct` (u16, 0.01 % of a 768-frame scale). Zero means old firmware; fall back to byte 3. The trace becomes float.
   - **Output Ring Health section:** `REQ_GET_STATUS` 26-31, each u32:
     - 26 underrun episodes
     - 27 refused blocks
     - 28 lowest pre-write fill (0xFFFFFFFF = none)
     - 29 worst input gap µs
     - 30 worst USB packet gap µs
     - 31 over-budget steps
   - **Also 32 and 33**, which the Mac doesn't show: S/PDIF input rate in mHz and VCXO trim in ppm × 100.
   - **Gate** all of these on the 0x03 status read, because old firmware answers 0 rather than stalling.
   - **Rescale** fill to the 512-frame ring (factor 768/512). Thresholds:
     - red below 1 frame, or at or above 512−64
     - yellow below target/4, or above target + 2 × batch
     - green otherwise
6. **Interrupt Monitor.** Decode 0x0D, 0x0F and 0x10 in `NotifyDecoder.cs`.
7. **Tests.**
   - Wire tests for 0x03 status and table parsing.
   - Name-probe logic.
   - Notify 0x0D, 0x0F and 0x10 parsing.
   - Buffer-stats fill.
   - CS noun names.

Hand-off: latency picker, source and board names (rename on the board, then check the Mac sees the same name), Stats ring health, and the CS Device group.

### Phase 2: Analyser sharing (M, about 3-4 days)

Mac references: `SpectrumAnalyser.swift` (`RtaOwnership`), `Documentation/rta_sharing_spec.md`; firmware `spectrum_analyser_spec.md` §7; commits 5e43c0e, 6542682 and b5fdeac.

1. **Handle `NOTIFY_EVT_RTA_CONFIG` 0x0D** in `DspDevice.ProcessNotifyPacket`. It is 17 bytes: the applied 12-byte RtaConfig at bytes 4-15, ParamSource at 16.
2. **Replace `RtaEngine`'s push / readback / three-strike rejection** (`RtaEngine.cs:312-406`) with the driving / following model:
   - **Own echo:** confirms the push. Until Link exists, "own" means Source = HostSet; from L1 on, it means `origin == own session`.
   - **Foreign config:** if tap, mask or order differs (a superset counts as a difference), follow it. Following means no push and no rejection count, and the views are given the effective selection.
   - **Taking control:** any user change of channels, tap or options, or **Take control**, takes control back. Showing or hiding a display does not. Never merge another console's channels into ours.
   - **While no view watches:** keep the last requested config. STOP keeps the ownership state.
   - **Bins:** read them whenever the analysed config is a single channel and a display draws the fine curve, whoever chose it.
   - **Fallback on old firmware:** read back until the first 0x0D arrives; after that, read back only while a push is unconfirmed.
3. **UI:** "Following another console" plus a **Take control** button, in the graph gear's SPECTRUM section and in the analyser window's status strip. Channel chips and overlays show the followed selection.
4. **Tests:** port `RtaSharingTests.swift` (21 tests), the single-host cases now and the multi-session cases in L1.

Hand-off: a UART or I2C host is the only other writer on USB alone. This is fully testable between consoles at the **L4 pause gate**.

## 4. DSPi Link

### Architecture on Windows

The Mac routes the **local UI through the hub's `CommandRouter` even with sharing off**, so ordering, origin attribution and locks are the same for the local window and for remote clients. Windows keeps that model, and cuts the seam *below* `DspDevice` rather than above it:

- **Every vendor transfer** already funnels through `DspDevice.ControlTransferOut/In` (`DspDevice.cs:1264-1351`, 212 internal callers) and `GetAllParams` (`:2659-2707`).
- **About 370 references** outside `DSPiConsole.Usb` use only the typed API, and **no LibUsbDotNet type** leaks out of `DspDevice.cs`.
- **The RTA engine** already sits behind `IRtaTransport`.

So:

```
MainViewModel ──► DspDevice (protocol facade, unchanged API)
                     │
                     ▼
               IDspTransport  (In/Out → status, notify stream with origin,
                     │         lock + exclusive section, identity)
        ┌────────────┼──────────────────┐
  HubTransport   NetworkTransport   (tests: FakeTransport)
  (local UI =    (ClientWebSocket
   session 1)     to a remote hub)
        │
  LinkHub ── CommandRouter ── UsbHubDevice ── UsbTransport (LibUsb, EP 0x83)
        ├── DeviceRegistry, SnapshotCache, NotifyRelay, PollScheduler
        ├── AuthStore, LinkSessionHandler ×N
        └── LinkServer (TcpListener + WebSocket) + DnsSdAdvertiser
```

A `DeviceManager` above the transports merges local and remote devices, playing the role of the Mac's `CompositeTransport`. Device-list ownership and auto-select move out of USB `ScanDevices` (`DspDevice.cs:942-969`) into this manager.

Component names mirror the Mac's (`networking_plan.md` §4), so the two can be reviewed line by line.

**Shared artefacts:** vendor a **tagged** dspi-link release into `third_party/dspi-link/`, holding the spec, `policy/commands.json` and `fixtures/`. Record the tag. If dspi-link has no tag yet, ask for one to be cut before L0.

### L3: Windows as a hub, core and server (XL, about 2-3 weeks)

1. **`LinkHub` core**, ported from the Mac's `LinkHub.swift` and friends:
   - **`HubTransport`:** the local UI is session 1 (admin, exempt from the in-flight cap). Session ids for remote clients start at 2, wrap, and skip 0, 1, 0xFFFF and ids still open.
   - **`CommandRouter`:** a per-device serial queue. Check order: policy (DENIED) → shutdown (NO_DEVICE) → lock (LOCKED) → in-flight cap 8 per remote session (RATE_LIMITED). Other duties:
     - bind each command to the device generation;
     - time out after 2 s, or 5 s for bulk;
     - keep the writer FIFO (64 entries, merged like the firmware coalesces, rolled back on failure) for origin attribution within a 0.5 s window;
     - **serve a client's 0xA0 as a chunked 0xA2 read, and a client's 0xA1 as 0xA3 writes, holding the device for the whole chunk session** (§9.1.1);
     - map WinUSB stall / timeout / not-connected to ERROR / TIMEOUT / NO_DEVICE;
     - apply RTA STOP arbitration (§7.15: swallow STOP while another session watched within 5 s, answering OK `01`).
   - **`PollScheduler`:** fan-out, 50 ms tick, 20 Hz max, 200000 bps per session, slots 0..15, half rate after 3 failures. **Unlike the Mac, run polls through the router**, so they can't tear a chunk session.
   - **`DeviceRegistry`:**
     - serial → lowest free handle, 60 s offline grace;
     - name order: board name > stored name > "DSPi " + last 6 of the serial;
     - write a stored name onto an unnamed board once;
     - follow 0x10 events;
     - retry the identity read with backoff while a board boots.
   - **`SnapshotCache`:** patch from PARAM_CHANGED; refresh 150 ms after BULK_INVALIDATED. Re-reading instead of patching is allowed (§7.5), but costs a chunked read on Windows.
   - **`NotifyRelay`:** a 256-entry queue per session with its own u16 tag; on overflow, drop the oldest and send one RESYNC with reason 0.
   - **`AuthStore`** (`%LOCALAPPDATA%\DSPiConsole\link-auth.json`):
     - `hubID`, `hubName` (default "<PC name> DSPi Console") and `authMode` (default **Open / `none`**, per N5);
     - clients, each stored with a SHA-256 token hash;
     - pairing: a 120 s window, a 6-digit PIN by rejection sampling, killed after 5 failures; 5 failures per address per minute block that address for 60 s;
     - revocation closes the client with 4002; a role change applies from the next command.
   - **`LinkSessionHandler`** (socket-free, unit-tested):
     - hello caps: `cmd notify poll snapshot lock rename web`; limits 65536 / 8192 / 8 / 20 / 200000;
     - in `none` mode, open an admin session immediately;
     - malformed JSON closes with 4000;
     - an unknown binary type, and FWDATA, get UNSUPPORTED; a payload over 8192 gets TOO_LARGE;
     - admin checks on `auth.*` and `hub.*`;
     - rename past the in-flight limit answers `busy`;
     - answer the web UI's `{"t":"ping"}` with `unknown_type`; do not close the connection.
2. **`LinkServer` (N2):**
   - **Socket:** `TcpListener` on `[::]` with `DualMode`, port 11915 by default.
   - **Peer gate** admits:
     - loopback, RFC 1918, 169.254/16, fe80::/10, ULA and CGNAT 100.64/10;
     - any on-link subnet, taken from `NetworkInterface`.
   - **Origin check (1.2):** compare against our own IPs, hostname and `<host>.local`, never the `Host` header.
   - **Routes:**
     - `/dspi/v1/info` (with CORS `*` on that route only);
     - `/` serves the web bundle: a type allow-list, `..` rejected, `no-cache`;
     - anything else is 404.
   - **Keepalive:** ping every 10 s; close 1001 after 30 s idle; close 4001 after 30 s without auth.
   - **Backpressure:** a bounded outbound channel per session. While the client lags, shed POLL frames and fold NOTIFY into one owed RESYNC; close 1011 when it has been stuck for 10 s.
   - **Fragments:** reassemble up to 65536 bytes, else close 4000.
3. **`DnsSdAdvertiser` (N3):**
   - `_dspi._tcp`, instance name = hub name.
   - TXT: `v`, `hid`, `kind=console`, `auth`, `n`, and `d` (dropped above 400 bytes), plus `web=1`.
   - Re-register on a rename, an access-mode change or a device-list change.
4. **Web UI:** build `js/apps/web` at the vendored tag (`npm install && npm run build` in `js/`). Ship `dist/` as Content in `DSPiConsole/Web/`. The Mac's copy is a frozen 1.1 build, so ours will be newer; that's fine, since the page gates its features on caps.
5. **Firewall** (the biggest field risk, §9.1.1):
   - The first non-loopback listen by an unpackaged exe shows the Defender prompt. If the user dismisses it, Windows creates a silent **block** rule.
   - On enabling sharing, check for an allow rule for `app\DSPiConsole.exe` on the Private profile (`INetFwPolicy2`). If it is missing, offer an elevated add (a `runas` helper using `netsh advfirewall` or COM).
   - Check the network category (`INetworkListManager`). On a **Public** network (where mDNS and inbound are blocked), tell the user to switch it to Private.
6. **Settings › Networking (hub half):**
